# ZK Nexus Standard v1.0

**Purpose:** Master core standard defining file naming (`ZNS-NC`), object ID registry (`ZNS-OID`), metadata headers (`ZNS-MD`), status lifecycles (`ZNS-SS`), version control (`ZNS-VC`), workspace module hierarchy, and access rules across ZK Nexus.

---

## 1. File & Directory Naming Standard (`ZNS-NC`)

All files and directories created within ZK Nexus MUST strictly follow these naming rules:

### 1.1 Directory Naming
- **Format:** Title Case with spaces for standard directories (e.g., `Client Delivery`, `Operational Workflow Engine`).
- **Module Directories:** Numbered prefix + Title Case with underscores for top-level root modules (e.g., `00_Command Center`, `01_Business`, `02_Projects`, `03_Knowledge`, `04_Workforce`, `05_Systems`, `06_Resources`, `07_Templates`, `08_Logs`, `99_Archive`).
- **No Special Characters:** Avoid symbols (`&`, `@`, `$`, `%`, `#`) or punctuation in folder names.

### 1.2 File Naming
- **Format:** kebab-case in lower-case with hyphens separating words (e.g., `lead-qualification-sop.md`, `business-registry.md`).
- **Numbered Governance & SOP Files:** 3-digit zero-padded number prefix followed by Title Case or kebab-case title (e.g., `001_Vision.md`, `002_Mission.md`, `SOP-SDR-001_WhatsApp-Outreach.md`).
- **Object ID Files:** Use official `{PREFIX}-{NNN}` ID as part of the filename when creating indexed documents (e.g., `TMP-001_Proposal_SDR-Pilot.md`).
- **Dates:** Format as `YYYY-MM-DD` (e.g., `2026-07-28_weekly-summary.md`).
- **Prohibited Words:** NEVER use words like `final`, `final-final`, `updated`, `new`, `old`, `latest`, or `v2` in filenames. Versioning is tracked via metadata and version history tables.

## 2. Metadata Header Standard (`ZNS-MD`)

Every Markdown file created or updated in ZK Nexus MUST begin with a YAML frontmatter metadata header block formatted as follows:

```yaml
---
Title: [Document Title]
ID: [ZNS Object ID, e.g., RUL-001, SOP-003, IDX-011]
Type: [Standard | Protocol | SOP | Registry | Strategy | Blueprint | Template | Report]
Module: [Root Module, e.g., 00_Command Center, 01_Business, 04_Workforce]
BU: [Target BU: ZK Revenue Ops | DAE Ecosystem | All]
Status: [Draft | Review | Active | Archived]
Version: [Semantic Version, e.g., 1.0, 1.1, 2.0]
Created: [YYYY-MM-DD]
Updated: [YYYY-MM-DD]
Owner: [Human Founder | Raiz Iszra | AI Worker ID]
Related: [Comma-separated list of related Object IDs or filenames]
---
```

### 2.1 Metadata Updating Rules
- Whenever any content within a file is modified, the `Updated` date MUST be updated to the current date (`YYYY-MM-DD`).
- When a document undergoes a significant revision, increment the `Version` number according to `ZNS-VC`.
- Changes in document approval status MUST be reflected in the `Status` field.

## 3. Object ID Registry Standard (`ZNS-OID`)

Every major workspace entity, document, template, system, or asset MUST be assigned a unique, non-reusable Object ID.

### 3.1 ID Format
- **Pattern:** `{PREFIX}-{NNN}`
- `{PREFIX}` is a 3-letter uppercase category code.
- `{NNN}` is a 3-digit zero-padded sequential integer (e.g., `001`, `002`, `015`).

## 4. Status Lifecycle Standard (`ZNS-SS`)

All documents in ZK Nexus move through a strict 4-stage lifecycle:

```
[ Draft ] ──> [ Review ] ──> [ Active ] ──> [ Archived ]
```

1. **Draft:** Initial creation stage. All new operational content created by AI or human contributors must be placed in `02_Projects/` in `Draft` status.
2. **Review:** Staged content that is complete and pending Human Founder evaluation.
3. **Active:** Approved, operational source of truth documents located in root modules (`00` through `07`).
4. **Archived:** Historical, superseded, or inactive documents moved to `99_Archive/`.

### 4.1 Active Document Protection Rule
- **Read-Only to AI:** Documents marked with `Status: Active` are strictly read-only for direct automated modifications by AI workers.
- **Modification Protocol:** To update an `Active` document, AI workers MUST create a copy as a `Draft` in `02_Projects/`, apply the changes, and submit the draft to the Human Founder for promotion to `Active`.

## 5. Version Control Standard (`ZNS-VC`)

- **Format:** `vMAJOR.MINOR` (e.g., `v1.0`, `v1.1`, `v2.0`).
- **Minor Revisions (`v1.1`, `v1.2`):** Incremented for minor edits, typo fixes, field additions, or clarification.
- **Major Revisions (`v2.0`):** Incremented for structural overhauls, rule changes, or major policy updates.
- **Version History Table:** Every document MUST contain a Change Log table at the bottom of the file:

```markdown
---
## Change Log
| Date | Actor | Change |
|------|-------|--------|
| 2026-07-28 | AI-005 | Updated section 3 prefix table |
```

## 6. Workspace Hierarchy & Access Rules

### 6.1 10-Module Top-Level Hierarchy
- `00_Command Center` — Workspace entry points, indexes, master registries, health reports.
- `01_Business` — Live business unit operations and governance.
- `02_Projects` — Active work, staging area, draft workspace.
- `03_Knowledge` — Knowledge base, SOPs, research backlog.
- `04_Workforce` — AI and human roles, governance rules, onboarding protocols.
- `05_Systems` — Code, scripts, web apps, automations, APIs.
- `06_Resources` — Static assets, logos, brand guidelines.
- `07_Templates` — Reusable blueprints and template files.
- `08_Logs` — Immutable append-only audit records.
- `99_Archive` — Historical and retired files.

### 6.2 Access Matrix & Permissions
- **Read Access:** AI workers have universal read access across all 10 root modules.
- **Write Access (Direct):** AI workers may write freely ONLY within `02_Projects/` (staging zone).
- **Write Access (Approved):** Writing directly to root modules (`01`, `03`, `04`, `05`, `06`, `07`) requires explicit Human Founder approval.
